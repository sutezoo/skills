# spec-from-code

実装コードと、要件定義書・手書き仕様書を読み合わせて、画面仕様書（screen-spec スキーマに適合するJSON）を生成する。

このスキルの肝は3つ。第一に、コードはフロントエンドだけでは画面の振る舞いを語らない。
通信先で同期処理されるか待ちを伴うかで画面の状態が変わるため、フロントとバックを縦断して読む。
第二に、出力は実装の写しではなく、コードを知らない人が読んで完結する画面仕様書である。
コードの語彙（フレームワーク名、HTTPステータス番号、変数名）を、画面の振る舞いの言葉に翻訳する。
第三に、**コード（実装の現状 as-is）と要件定義書・手書き仕様書（あるべき姿 to-be）が食い違ったら、仕様書を正とする**。
spec 本体には to-be を反映し、コードとの差分は実装乖離レポートに記録して、黙って捨てない。

## 出力の契約

主成果物は `references/screen-spec.schema.json` に適合するJSON（画面仕様書）。各フィールドの意味と設計意図は
`references/screen-spec.schema.md` に書かれている。**作業前に必ずこの2つを読む。**
出力の完成形の実例は `assets/example.SCR-030.json`（プロフィール編集画面）にある。

副成果物として、コードと仕様書の食い違いを記録する**実装乖離レポート**（`assets/template.deviation-report.json` の形式）を出力する。食い違いが無ければ deviations は空でよい。

スキーマの構造は要素中心と状態中心の2軸からなる。要素中心（elements）は各UI要素が自身の制約・
入力検証・状態別表示を持つ。状態中心（behaviorMatrix）は状態ごとに起きうるイベントと処理・遷移先を
持ち、状態×イベントの網羅性を担う。この2軸は補完関係にある。

## 正準ソースの優先順位（食い違いの解決ルール）

複数の入力が食い違うとき、次の優先順位で**上位を正**とする（裁量で都度判断しない）:

**要件定義書 ＞ 手書き仕様書 ＞ コード**

- spec(JSON) 本体には、勝ったソース（通常は仕様書）の値＝あるべき姿を反映する。
- コードとの差分は実装乖離レポートの `deviations[]` に「code（現状）/ spec（あるべき）/ adoptedSource（根拠）/ implication（含意）」で記録する。
- この優先順位はプロジェクトで変える場合があるので、レポートの `sourcePriority` に明示する。

## 手順

### 1. 準備（必ず最初に行う）

- `references/screen-spec.schema.json` と `references/screen-spec.schema.md` を読み、出力契約を把握する。
- `references/writing-style.md` を読み、文章のルール（特に実装語を持ち込まない翻訳）を把握する。
- `references/code-reading-guide.md` を読み、どこから何を抽出するかを把握する。
- `assets/example.SCR-030.json` を見て、完成形の水準を把握する。
- `assets/template.deviation-report.json` を見て、乖離レポートの形式を把握する。
- **入力に要件定義書・手書き仕様書があれば、この時点で読み込む。** 無ければコードのみで進め、その旨を後で報告する。

### 1.5. 正準ソースとの照合（仕様書がある場合）

コードから読み取った内容と、要件定義書・手書き仕様書の記述を突き合わせる。

- 一致する項目はそのまま spec に反映する。
- **食い違う項目**は、優先順位に従い仕様書（to-be）を正として spec に反映し、`deviations[]` に1件記録する。
  典型例: 制約値（最大長 50 vs 100）、入力検証の有無、エラー文言、遷移先、振る舞いの有無。
- **仕様書にあってコードに無い**振る舞いは、spec に to-be として起こし、deviation に「未実装の疑い」として記録する。
- **コードにあって仕様書に無い**振る舞いは、仕様書の記載漏れか実装の余剰かを断定せず、spec には現状を残しつつ deviation に「仕様書に記載なし・要確認」として記録する（黙って消さない）。
- 仕様書からも読み取れない値は推測で埋めず、手順5に従い `undefined` にする。



どの画面の仕様書を作るかを確定する。1画面 = 1JSONファイル。複数画面を頼まれたら画面ごとに分ける。
画面のフロントエンド・コンポーネントを起点ファイルとして特定する。

### 3. コードの縦断的な読み取り

`code-reading-guide.md` に従い、フロントの起点から通信を辿り、通信先のバックエンドまで読む。
特に次を見極める。

- 通信が同期処理か、待ちを伴う処理か（→ 状態に「待ち状態」が要るかが決まる）。
- 通信結果がどう分岐するか（成功・各種エラー・競合など）。
- 入力検証がフロント・バックのどちらに、何があるか。
- エラーメッセージの正確な文言（文字列リテラル）。

### 4. 構造化（スキーマへの当てはめ）

読み取った内容を、コードの語彙を翻訳しながらスキーマの各セクションに当てはめる。

- states: 画面が取りうる状態。状態名は実装の変数名でなく画面の意味を表す日本語にする。
- events: 生のトリガーだけを列挙する。結果による枝分かれは events に入れず behaviorMatrix の branches で表す。
- elements: 画面要素をトップレベルに挙げる。ページに直接置かれたボタン・入力欄や、グローバルな
  トーストは単独要素として置く。複数要素のまとまり（ダイアログなど）だけをコンテナにし、その中に
  個別要素(children)を置く。すべての要素を入れる包括的な「本体」のような器は作らない（階層が無駄に
  深くなる）。ダイアログを「OKで遷移」と潰さず、中のボタン・入力欄を個別要素として挙げる。子が1つ
  しかないバナーやトーストは単独要素にする。状態別表示は visibility の1値（hidden / visible /
  operable / conditional）で持ち、「非表示なのに操作可」は作らない。制約・入力検証は個別要素に凝集
  させる。トップレベルの要素・コンテナ名は画面内で一意、コンテナ内の要素名はそのコンテナ内で一意にする。
- behaviorMatrix: 状態ごとに、起きうるイベントの処理と遷移先を書く。複数結果に分かれるなら branches を使う。
  イベントがボタン押下・入力変更など特定要素の操作で起きる場合は、必ず source に「コンテナ名／要素名」を書く。
  source は要素を起点に振る舞いを追う見方（要素中心ビュー）の土台になるため、要素操作のイベントでは省略しない。
  画面表示時の取得・通信結果の受信・タイマーなど、要素操作によらないシステム起点のイベントだけ source を省く。
- navigation: 入口・出口。対象画面のコードから特定できなければ空にする。
- layout: モック画像への参照のみ。図は持たない。
- status: 生成直後は必ず `"draft"` を付ける。

翻訳の例（`writing-style.md` 参照）: `max_length=50` は「50文字以内」、HTTPの409は
「他の利用者が先に更新していた場合」。フレームワーク名・関数名・ステータス番号は出力に残さない。

### 5. 判断できないことの扱い

コードから判断できないものは推測で埋めない。該当する振る舞いに `undefined: true` を付けるか、
空にできる項目は空にする。典型例は、画面の利用目的、特定できない遷移先、未実装の異常系挙動、
文言が特定できないメッセージ。これらは生成後に人間へ報告する（手順7）。

### 6. 自己検証（出力前に必ず行う）

生成したJSONを出力する前に、次を確認する。スキーマ適合と意味的整合の両方を見る。

- スキーマ適合: `references/screen-spec.schema.json` に適合するか。検証スクリプトが使えるなら
  jsonschema で機械的に確認する。
- 意味的整合（スキーマでは検査されない。`screen-spec.schema.md` の該当節に基づく）:
  - 初期状態（initial: true）はちょうど1つか。
  - コンテナ名は画面内で一意か。個別要素名は同一コンテナ内で一意か。
  - コンテナ・個別要素の displayByState のキーが、すべて states に実在するか。
  - コンテナが hidden の状態で、その子要素が visible/operable/conditional を主張していないか（親子整合）。
  - behaviorMatrix の state と event が、states・events に実在するか。
  - behaviorMatrix の source が指す「コンテナ／要素」が実在するか。
  - 遷移先 to（branches の to を含む）が states に実在するか（null は可）。
  - branches と process/to を同時に持っていないか（排他）。
  - 実装語（フレームワーク名・関数名・変数名・HTTPステータス番号）が文字列値に混入していないか。
- 網羅性: behaviorMatrix が、各状態で起きうるイベントを取りこぼしていないか。状態×イベントで
  考慮が抜けたセルがないか。抜けているが挙動が不明なら undefined にする。

### 7. 生成結果の報告

画面仕様書(JSON)と**実装乖離レポート(JSON)**を提示するとともに、人間が確認すべき点を簡潔に伝える。少なくとも次を報告する。

- 仕様書とコードの**食い違い（deviations）の件数と要点**。特に「実装が要修正の疑い」のものは強調する。
- 要件定義書・手書き仕様書が無くコードのみで起こした場合は、その旨（to-be が未確認である注意）。
- `undefined` にした箇所と、その理由（コード・仕様書のどちらからも判断できなかった点）。
- 空にした項目（navigation など）。
- 翻訳・解釈に判断が入った箇所。

生成物は人間がレビューして確定させる叩き台である。確定の判断は人間に委ねる。
乖離レポートの deviations は、後段 spec-to-test で to-be を期待値とするテストになり、未修正コードでは fail することで検出される。

## やってはいけないこと

- コードと仕様書の食い違いを**黙って一方に寄せる**こと。優先順位で解決し、必ず deviations に記録する。
- 実装の語彙を出力に残すこと（フレームワーク名、関数名、変数名、HTTPステータス番号など）。
- 複数の画面要素を1つにまとめて潰すこと（「ダイアログ。OKで遷移」のように、中のボタンや入力欄を
  個別要素として起こさないこと）。すべての画面要素を個別に挙げる。
- すべての要素を入れる包括的なコンテナ（「本体」「ページ全体」など）を作ること。ページ直下の要素は
  トップレベルの単独要素として置き、まとまりが必要なもの（ダイアログなど）だけをコンテナにする。
- 状態別表示で「非表示なのに操作可」のような矛盾した値を作ること。visibility の1値で表す。
- サーバ側の検証とクライアント側の検証を区別して書くこと。利用者から見た一つのエラーとして扱う。
- コードから判断できないことを推測で埋めること。undefined にして人間に回す。
- コードに存在しないエラーメッセージを創作すること。
- 確度を示すタグを各記述に付けること。
- 概要・画面目的・利用シーンなどの説明文を仕様書に書き足すこと。これは詳細仕様であり、読み手が既に
  知っている前提の説明は不要で、解釈のずれを生むだけになる。スキーマにある項目だけを埋める。
- 要素操作で起きるイベントの source を省略すること。ボタン押下・入力変更などは必ず source を付ける。
- 1つのファイルに複数画面を詰め込むこと。1画面1ファイル。
