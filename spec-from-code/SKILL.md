# spec-from-code

実装コードと、意図メモ・要件定義書・手書き仕様書を読み合わせて、画面仕様書（screen-spec スキーマに
適合するJSON）を生成する。

このスキルの肝は4つ。第一に、コードはフロントエンドだけでは画面の振る舞いを語らない。
通信先で同期処理されるか待ちを伴うかで画面の状態が変わるため、フロントとバックを縦断して読む。
第二に、出力は実装の写しではなく、コードを知らない人が読んで完結する画面仕様書である。
コードの語彙（フレームワーク名、HTTPステータス番号、変数名）を、画面の振る舞いの言葉に翻訳する。
第三に、**コード（実装の現状 as-is）と意図メモ・要件定義書・手書き仕様書（あるべき姿 to-be）が
食い違ったら、to-be を正とする**。spec 本体には to-be を反映し、コードとの差分は実装乖離レポートに
記録して、黙って捨てない。第四に、**状態×イベントの全セルを埋める（全域性）**。書けないセルも
`undefined`（判断できない）か `notApplicable`（発生し得ない。理由必須）で明示し、空欄を残さない。

## 開発プロセス上の位置づけ

このスキルは、画面を1つ実装するたびに回すことを前提にする（全画面の実装が終わってからの一括生成は、
実装時の詳細仕様の記憶・コンテキストが失われ、乖離の修正コストが上がる）。1画面のサイクルは
「実装 → 本スキルで仕様化 → スキーマ検証と lint → 人間が乖離と undefined・該当なしを判定 →
修正 → spec-to-test でテスト条件表を導出し、各条件をテストレベルへ振り分けてからテストを実装」。

成果物の役割分担を取り違えないこと。**いま存在するバグを見つけるのは、意図メモと実装の乖離
（deviations）、および全域性検査であぶり出される undefined セルである。** 導出されたテストの主な
価値は、今後の変更で挙動が壊れたときに教えてくれる回帰保護にある。

## 入力（4つの文書）

| 入力 | 役割 | 無い場合 |
| --- | --- | --- |
| コード | as-is（実装の現状） | 必須 |
| 意図メモ（`<画面ID>.intent.md`） | to-be の第一情報源。EARS形式の短文集合（`references/intent-memo-guide.md`） | 明示的に警告する（後述） |
| 要件定義書・手書き仕様書 | to-be の補助情報源 | 無ければコードと意図メモで進める |
| 共通仕様（common-spec.json） | 画面横断の振る舞いの定義。画面はこれを暗黙に継承 | 無ければ overrides も書かない |

**意図メモが無い場合、to-be の情報源が実質空になり、生成される仕様書はコードの鏡写しになる。**
そこから導出したテストは「コードがやっていることを、コードがやっているか」の同語反復になり、
いま存在するバグを検出できない（オラクルの独立性がない）。この場合は次のいずれかを行う。

- 依頼者に意図メモの作成を促す。要件定義書があれば、**コードを見る前に**要件定義書から意図メモの
  叩き台を起こして確認してもらう（コードを見てから書くと独立性が失われる）。
- それでも無いまま進める場合は、生成結果の報告で「to-be 未確認。この仕様書は実装の現状の文書化で
  あり、乖離検出は働いていない」と必ず明示する。黙って進めない。

## 出力の契約

主成果物は `references/screen-spec.schema.json`（v2.0）に適合するJSON（画面仕様書）。各フィールドの
意味と設計意図は `references/screen-spec.schema.md` に書かれている。**作業前に必ずこの2つを読む。**
出力の完成形の実例は `assets/example.SCR-030.json`（灯台検索画面）にある。

副成果物として、コードと意図メモ・仕様書の食い違いを記録する**実装乖離レポート**
（`assets/template.deviation-report.json` の形式）を出力する。食い違いが無ければ deviations は空でよい。

スキーマの構造は要素中心と状態中心の2軸からなる。要素中心（elements）は各UI要素が自身の制約・
入力検証・状態別表示を持つ。状態中心（behaviorMatrix）は状態ごとに起きうるイベントと処理・遷移先を
持ち、状態×イベントの全域性を担う。この2軸は補完関係にある。

## 正準ソースの優先順位（食い違いの解決ルール）

複数の入力が食い違うとき、次の優先順位で**上位を正**とする（裁量で都度判断しない）:

**意図メモ ＞ 要件定義書 ＞ 手書き仕様書 ＞ コード**

- spec(JSON) 本体には、勝ったソースの値＝あるべき姿を反映する。
- コードとの差分は実装乖離レポートの `deviations[]` に「code（現状）/ spec（あるべき）/ adoptedSource（根拠）/ implication（含意）」で記録する。
- この優先順位はプロジェクトで変える場合があるので、レポートの `sourcePriority` に明示する。
- 意図メモは網羅しない（数行から十数行）。メモに無い詳細をコードから補うのは正常であり、乖離ではない。

## 手順

### 1. 準備（必ず最初に行う）

- `references/screen-spec.schema.json` と `references/screen-spec.schema.md` を読み、出力契約を把握する。
- `references/writing-style.md` を読み、文章のルール（特に実装語を持ち込まない翻訳）を把握する。
- `references/code-reading-guide.md` を読み、どこから何を抽出するかを把握する。
- `assets/example.SCR-030.json` を見て、完成形の水準を把握する。
- `assets/template.deviation-report.json` を見て、乖離レポートの形式を把握する。
- **入力に意図メモ・要件定義書・手書き仕様書があれば、この時点で読み込む。** 意図メモが無ければ
  「入力」の節に従って対応する。
- **共通仕様（common-spec.json）があれば読み込む**（`references/common-spec.schema.json` が契約。
  無いプロジェクトで新たに作る場合は `assets/template.common-spec.json` から起こす）。

### 1.5. 正準ソースとの照合

コードから読み取った内容と、意図メモ・要件定義書・手書き仕様書の記述を突き合わせる。

- 一致する項目はそのまま spec に反映する。
- **食い違う項目**は、優先順位に従い to-be を正として spec に反映し、`deviations[]` に1件記録する。
  典型例: 制約値（最大長 50 vs 100）、入力検証の有無、エラー文言、遷移先、振る舞いの有無。
- **意図メモ・仕様書にあってコードに無い**振る舞いは、spec に to-be として起こし、deviation に「未実装の疑い」として記録する。
- **コードにあって意図メモ・仕様書に無い**振る舞いは、記載漏れか実装の余剰かを断定せず、spec には現状を残しつつ deviation に「意図メモ・仕様書に記載なし・要確認」として記録する（黙って消さない）。
- どのソースからも読み取れない値は推測で埋めず、手順5に従い `undefined` にする。

### 2. 対象画面の確定

どの画面の仕様書を作るかを確定する。1画面 = 1JSONファイル。複数画面を頼まれたら画面ごとに分ける。
画面IDは `SCR-数字3桁`。既存の画面仕様書群と重複しないIDを割り当てる。
画面のフロントエンド・コンポーネントを起点ファイルとして特定する。

### 3. コードの縦断的な読み取り

`code-reading-guide.md` に従い、フロントの起点から通信を辿り、通信先のバックエンドまで読む。
特に次を見極める。

- 通信が同期処理か、待ちを伴う処理か（→ 状態に「待ち状態」が要るかが決まる）。
- 通信結果がどう分岐するか（成功・各種エラー・競合など）。
- 入力検証がフロント・バックのどちらに、何があるか。
- エラーメッセージの正確な文言（文字列リテラル）。
- 一覧要素の0件時の挙動（emptyBehavior）。
- 要素が読み書きするテーブル・カラム（dataRef。特定できれば書く）。

### 4. 構造化（スキーマへの当てはめ）

読み取った内容を、コードの語彙を翻訳しながらスキーマの各セクションに当てはめる。

- states: 画面が取りうる状態。状態名は実装の変数名でなく画面の意味を表す日本語にする。
- events: 生のトリガーだけを列挙する。結果による枝分かれは events に入れず behaviorMatrix の branches で表す。
- elements: 画面要素をトップレベルに挙げる。kind は enum から選ぶ（自由文字列は書けない）。
  ページに直接置かれたボタン・入力欄や、グローバルなトーストは単独要素として置く。複数要素の
  まとまり（ダイアログなど）だけをコンテナにし、その中に個別要素(children)を置く。すべての要素を
  入れる包括的な「本体」のような器は作らない。ダイアログを「OKで遷移」と潰さず、中のボタン・
  入力欄を個別要素として挙げる。子が1つしかないバナーやトーストは単独要素にする。状態別表示は
  visibility の1値（hidden / visible / operable / conditional）で持ち、「非表示なのに操作可」は
  作らない。制約・入力検証は個別要素に凝集させる。種別ごとの記述義務（テキスト入力なら
  maxLength・validations・displayByState、一覧なら emptyBehavior など）はスキーマが強制する。
  トップレベルの要素・コンテナ名は画面内で一意、コンテナ内の要素名はそのコンテナ内で一意にする。
- behaviorMatrix: **全状態×全イベントのセルを埋める（全域性）。** 各セルは process/to・branches・
  undefined・notApplicable のちょうど1つ。結果が複数に分かれるなら branches を使う。その状態では
  イベントが発生し得ないセルは `notApplicable` に理由（例: この状態では検索ボタンが押せないため）を
  書く。発生するが何も起きないことが仕様なら process「何もしない」で書く（notApplicable にしない）。
  イベントがボタン押下・入力変更など特定要素の操作で起きる場合は、必ず source に
  「コンテナ名／要素名」を書く。source は要素を起点に振る舞いを追う見方（要素中心ビュー）の土台に
  なるため、要素操作のイベントでは省略しない。画面表示時の取得・通信結果の受信・タイマーなど、
  要素操作によらないシステム起点のイベントだけ source を省く。
- navigation: 入口・出口。from / to は画面ID（SCR-NNN）で書く（自由文字列は書けない）。
  対象画面のコードから特定できなければ空にする。
- commonSpec / overrides: 共通仕様があれば commonSpec にパスを書く。この画面が共通仕様から逸脱する
  振る舞いを持つ場合のみ、overrides に rule / behavior / reason を宣言する（reason 必須）。
  逸脱に根拠が見つからない場合は、overrides でなく deviation（書き揺れ・要確認）として扱う。
- layout: モック画像への参照のみ。図は持たない。
- status: 生成直後は必ず `"draft"` を付ける。

翻訳の例（`writing-style.md` 参照）: `max_length=50` は「50文字以内」、HTTPの409は
「他の利用者が先に更新していた場合」。フレームワーク名・関数名・ステータス番号は出力に残さない。

### 5. 判断できないことの扱い

どのソースからも判断できないものは推測で埋めない。該当する振る舞いに `undefined: true` を付けるか、
空にできる項目は空にする。典型例は、特定できない遷移先、未実装の異常系挙動、文言が特定できない
メッセージ。「発生し得ない」と「判断できない」を混同しない（前者は notApplicable、後者は undefined）。
undefined は生成後に人間へ報告する（手順7）。

### 6. 機械検証（出力前に必ず行う）

生成したJSONに対して、検証スクリプトを実行する。目視チェックリストは使わない（lint が正）。

```
python scripts/validate.py <spec.json> [--common-spec <common-spec.json>]
```

これが第一層（スキーマ適合: 構造・型・enum・種別ごとの記述義務・振る舞い4値の排他）と第二層の
単一ファイル分（全域性・参照の実在・初期状態がちょうど1つ・親子の表示整合・overrides の実在・
実装語の混入）を検査する。エラーが出たら修正して再実行し、通ってから出力する。

複数画面が揃っているプロジェクトでは、横断検査と生成も回す。

```
python scripts/lint_screens.py <specディレクトリ> --roots <入口画面ID>   # 到達可能性検査
python scripts/generate.py <specディレクトリ> --out <出力先>             # 画面一覧・遷移図・入出力一覧
```

スクリプトが実行できない環境では、`screen-spec.schema.md` の「検証の三層構造」の検査項目を
手動で確認する（例外的な代替手段。結果の報告にその旨を書く）。

### 7. 生成結果の報告

画面仕様書(JSON)と**実装乖離レポート(JSON)**を提示するとともに、人間が確認すべき点を簡潔に伝える。
人間のレビューは空欄探しではなく判定に集中してもらう。少なくとも次を報告する。

- 意図メモ・仕様書とコードの**食い違い（deviations）の件数と要点**。特に「実装が要修正の疑い」の
  ものは強調する。これが「いま存在するバグ」の候補である。
- `undefined` にした箇所と、その理由。これが「未定義動作」の候補である。
- `notApplicable` にしたセルの件数。理由が自明でないものは個別に挙げ、「これは本当に発生し得ないか」の判定を求める。
- overrides を宣言した箇所と、逆に「共通仕様と食い違うが根拠が無いため deviation にした」箇所。
- 意図メモが無くコードのみで起こした場合は、その旨（to-be 未確認であり乖離検出が働いていない注意）。
- 空にした項目（navigation など）。
- 翻訳・解釈に判断が入った箇所。

生成物は人間がレビューして確定させる叩き台である。確定の判断は人間に委ねる。
乖離レポートの deviations は、後段 spec-to-test で to-be を期待値とするテストになり、未修正コードでは
fail することで検出される。

## やってはいけないこと

- コードと意図メモ・仕様書の食い違いを**黙って一方に寄せる**こと。優先順位で解決し、必ず deviations に記録する。
- 意図メモが無いまま**黙って**コードだけから仕様書を起こすこと。起こす場合は to-be 未確認の警告を必ず付ける。
- **意図メモの叩き台をコードを見てから書く**こと。オラクルの独立性が失われ、乖離検出が空振りする。
- behaviorMatrix にセルの空欄（未記載の状態×イベント）を残すこと。全セルを4値のいずれかで埋める。
- 「判断できない」セルを notApplicable にする、または「発生し得ない」セルを undefined にすること。
  notApplicable は発生し得ない根拠を書けるときだけ使う。
- 共通仕様からの逸脱を overrides の宣言なしに書くこと（書き揺れと区別できなくなる）。
- 実装の語彙を出力に残すこと（フレームワーク名、関数名、変数名、HTTPステータス番号など）。
- 複数の画面要素を1つにまとめて潰すこと（「ダイアログ。OKで遷移」のように、中のボタンや入力欄を
  個別要素として起こさないこと）。すべての画面要素を個別に挙げる。
- すべての要素を入れる包括的なコンテナ（「本体」「ページ全体」など）を作ること。ページ直下の要素は
  トップレベルの単独要素として置き、まとまりが必要なもの（ダイアログなど）だけをコンテナにする。
- 状態別表示で「非表示なのに操作可」のような矛盾した値を作ること。visibility の1値で表す。
- サーバ側の検証とクライアント側の検証を区別して書くこと。利用者から見た一つのエラーとして扱う。
- コードから判断できないことを推測で埋めること。undefined にして人間に回す。
- コードに存在しないエラーメッセージを創作すること。
- 確度を示すタグを各記述に付けること。
- 概要・画面目的・利用シーンなどの説明文を仕様書に書き足すこと。これは詳細仕様であり、読み手が既に
  知っている前提の説明は不要で、解釈のずれを生むだけになる。スキーマにある項目だけを埋める。
- 要素操作で起きるイベントの source を省略すること。ボタン押下・入力変更などは必ず source を付ける。
- 1つのファイルに複数画面を詰め込むこと。1画面1ファイル。
- validate.py を通さずに出力すること。
