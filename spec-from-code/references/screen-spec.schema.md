# 画面仕様書スキーマ 解説

`screen-spec.schema.json`（JSON Schema Draft 2020-12、schemaVersion 2.0）の設計意図と、
スキーマ単体では表現できない整合ルールをまとめる。このスキーマは3者の共有契約である。

- `spec-from-code`: コード・意図メモ・仕様書を読み、このスキーマに適合するJSONを出力する
- Viewer: このスキーマのJSONを人間可読に表示・編集する
- `spec-to-test`: このスキーマのJSONを読み、テスト仕様書を導出する

v2.0 の目的は、仕様書の検証を「人が空欄を探す」作業から「機械が判定する」作業に変えることにある。
未定義動作の検出と画面挙動の統一性の確認は、あるべき全体が定義されて初めて機械的に判定できる。
そのために、kind の enum 化と種別ごとの記述義務、「該当なし」の一級市民化と全域性、
共通仕様への overrides、ID体系と画面間参照の正規化、の4つの拡張を入れている。

## 全体構造

トップレベルは識別情報（schemaVersion, id, title, type, status）、共通仕様との接続
（commonSpec, overrides）と、本体セクション（layout, navigation, states, events, elements,
behaviorMatrix）からなる。

設計の柱は2つの軸の併存である。

- 要素中心（elements）: トップレベルに、単独要素（ページ直下のボタン・入力欄や、グローバルな
  トーストなど）と、コンテナ（ダイアログのように複数要素をまとめるもの）を混在させる。
  単独要素は children を持たず、コンテナは children に個別要素を持つ。包括的な『本体』のような
  器は作らない（無駄に階層が深くなるため）。全画面要素を漏れなく挙げ、情報を要素の近くに凝集させる。
- 状態中心（behaviorMatrix）: 状態ごとに、起きうるイベントと処理・遷移先を持つ。
  状態×イベントの網羅性をここで判定する。

この2軸は重複ではなく補完である。要素中心は「各部品がどう見え、何を検証するか」を、
状態中心は「画面全体がどう動くか」を担う。

## v2.0 の4つの拡張

### 拡張1: kind の enum 化と種別ごとの記述義務

要素種別 `kind` は自由文字列ではなく enum である（テキスト入力・テキストエリア・数値入力・
日付入力・選択・チェックボックス・ラジオボタン・ファイル入力・ボタン・リンク・一覧・
表示テキスト・画像・バナー・トースト・ダイアログ）。用語の揺れ（「遷移」「移動」「画面切替」の
混在のような揺れ）を enum が構造的に潰し、spec-to-test の kind→観点マッピングの引き当ても
一意になる。

種別ごとに書くべき項目は `$defs/kindDuties` の `if/then` で条件付き必須にしている。

- テキスト入力・テキストエリア: constraints（maxLength 必須）・validations・displayByState
- 数値入力: constraints・validations・displayByState
- 日付入力: validations・displayByState
- 選択・チェックボックス・ラジオボタン・ファイル入力・ボタン・リンク: displayByState
- 一覧: emptyBehavior（0件時の表示・挙動）・displayByState

入力欄なのに桁数未定義、一覧なのに0件時挙動なし、といった観点漏れが、画面を書いた時点で
バリデーションエラーとして出る。統制するのは kind や visibility のような分類軸であり、
エラーメッセージの文言や処理の記述内容は縛らない。文言は画面に出る文字列そのものという
データであって、語彙ではないためである。

### 拡張2: 「該当なし」の一級市民化と全域性

`behaviorMatrix` の各セル（状態×イベント）は、次の4通りのちょうど1つを取る（排他）。

| 記法 | 意味 |
| --- | --- |
| `process` / `to`（+`message`） | 結果が一通りの定義済みの振る舞い |
| `branches` | 結果が複数に枝分かれする振る舞い |
| `undefined: true` | コードからも意図メモ・仕様書からも判断できない未確定箇所 |
| `notApplicable: { reason }` | この状態ではこのイベントが発生し得ないことの宣言（理由必須） |

そのうえで lint が、各状態の `on` が events の全件をちょうど1回ずつカバーすることを要求する
（全域性検査）。未記載を許さないことで「空欄イコール未定義動作の候補」と断定できるようになり、
レビューは空欄探しではなく「該当なしの理由が妥当か」「undefined をどう確定させるか」の判定に変わる。

境界線: `notApplicable` は「発生し得ない」専用である（例: その状態ではボタンが非表示）。
発生はするが何も起きないことが仕様なら、`process: "何もしない"` の定義済み振る舞いとして書く。
判断できない場合は `undefined: true` にする。

### 拡張3: 共通仕様への参照と overrides

日付フォーマット・エラー表示方式・二重送信防止・ページング挙動のような画面横断の振る舞いは、
共通仕様（`common-spec.schema.json` に適合するファイル）に一度だけ書く。各画面は `commonSpec`
でそのファイルを参照して全ルールを暗黙に継承し、逸脱する場合のみ `overrides` に
rule / behavior / reason を宣言する。

reason を必須にすることで、意図的な例外と単なる書き揺れを機械的に区別できる。挙動の統一性の
検査は「overrides 宣言なしに共通仕様と矛盾する記述がないか」という差分 lint に落ちる
（rule の実在はスクリプトが検査し、矛盾の内容判定は生成・レビュー時に行う）。

### 拡張4: ID体系と画面間参照の正規化

`id` は `SCR-数字3桁` に固定し、navigation の from / to は自由文字列ではなく画面IDに限定する。
これにより全ファイルを読む lint（`lint_screens.py`）で、どこからも遷移されない孤立画面と、
存在しない画面への遷移を到達可能性検査として検出できる。画面一覧と遷移図の自動生成
（`generate.py`）も、この参照の正規化が済んでいるため単純なスクリプトになっている。

## 主要な設計判断

### イベントは生のトリガーだけを定義する

`events` には「保存の実行」「保存結果の受信」のような生のトリガーだけを列挙する。
「成功したとき」「競合したとき」のような結果による枝分かれは events に入れず、
`behaviorMatrix` の各振る舞いの `branches` で表現する。

これにより events の定義と behaviorMatrix で使われるイベント名が1対1で対応し、
かつテストに必要な分岐の細かさは branches で保たれる。全域性検査（状態×イベントの全セル）も、
イベントが生のトリガーだけだから現実的な件数に収まる。

### 要素はコンテナで入れ子にし、全要素を網羅する

画面要素は、トップレベルに単独要素とコンテナを混在させて挙げる。ページに直接置かれた
ボタンや入力欄は単独要素としてトップレベルに置く。複数要素のまとまり（ダイアログなど）だけを
コンテナにし、その中に個別要素を置く。すべての要素を入れる包括的な『本体』のような器は作らない。
また「ダイアログ。OKで遷移」のように潰さず、ダイアログというコンテナの中に「OKボタン」を個別に挙げる。
子が1つしかないバナーやトーストは、コンテナにせず単独要素にする。

コンテナ自身も状態別表示を持つ（例: ダイアログは特定の状態でだけ表示される）。
コンテナが表示されている状態でも、その中の個別要素は表示・非表示が切り替わりうるため、
個別要素も独立に状態別表示を持つ。

### 状態別表示は visibility の1値で表す

各要素の状態別表示は、表示の有無と操作可否を別々の真偽値で持たず、1つの値で表す。
「非表示なのに操作可能」という矛盾を構造的に排除するためである。

- hidden（非表示）/ visible（表示・操作不可）/ operable（操作可）/ conditional（条件付き操作可、conditionに条件文）

表示専用の要素（ラベル・カウンタなど）は hidden / visible のみを使う。

### サーバ・クライアントを区別しない

これは画面の振る舞い仕様であり、実装の写しではない。入力検証は、クライアント検証も
サーバ検証（メール重複など）も区別せず、画面上のエラーの一つとして `validations` に並べる。

### レイアウトは画像参照

レイアウトはアスキーアートや座標で持たず、モック画像や Figma への参照（`layout.mockImage`）
だけを持つ。画面レイアウトだけは表構造にならないため、図そのものを仕様書に持たせない。

### 名前を識別キーにする

画面には `id`（SCR-NNN）を振るが、画面内の状態・イベント・要素には専用IDを振らず、名前を
識別キーにする。状態名・イベント名は画面内で一意にする。トップレベルの要素・コンテナの名前も
画面内で一意にする。コンテナ内の個別要素の名前は、そのコンテナ内で一意であればよい
（別コンテナに同名要素があってよい）。イベントが特定要素の操作で起きる場合、behaviorMatrix の
source で要素を指す。トップレベルの単独要素なら element のみ、コンテナ内要素なら container と
element で指す。

### dataRef は入出力一覧の生成用

各要素は任意で `dataRef`（参照先のテーブル・カラム）を持てる。入出力一覧はこの集計から
`generate.py` が生成する（手書きの入出力一覧は持たない）。特定できなければ省略する。

## 検証の三層構造

画面仕様書の検証は三層で行い、すべて CI に乗せる想定である。目視チェックリストは持たない
（スキーマと lint スクリプトが正）。

| 層 | 担当 | 内容 |
| --- | --- | --- |
| 第一層 | JSON Schema（`screen-spec.schema.json`） | 構造と型、enum、種別ごとの記述義務、振る舞い4値の排他、IDと参照のパターン |
| 第二層 | lint（`scripts/validate.py`・`scripts/lint_screens.py`） | スキーマでは書けない相互参照検査 |
| 第三層 | 生成（`scripts/generate.py`・spec-to-test） | 画面一覧・遷移図・入出力一覧・テストの導出 |

第二層の検査項目（`validate.py` = 単一ファイル）:

1. 初期状態（`states[].initial: true`）はちょうど1つ。
2. `displayByState` のキーは、すべて `states[].name` に実在する。
3. `behaviorMatrix[].state` / `on[].event` は states / events に実在する。
4. 遷移先 `to`（branches の `to` を含む）は states に実在する（null は可）。
5. 振る舞いは process/to・branches・undefined・notApplicable のちょうど1つ（4値の排他）。
6. 全域性: behaviorMatrix が全状態をちょうど1回ずつ持ち、各状態の `on` が events の全件を
   ちょうど1回ずつカバーする。未記載セルはエラー。
7. トップレベルの要素・コンテナ名は画面内で一意。コンテナ内の個別要素名は同一コンテナ内で一意。
8. コンテナが `hidden` の状態で、その子要素が `visible`/`operable`/`conditional` を主張しない（親子の表示整合）。
9. `behaviorMatrix[].on[].source` が指す「コンテナ／要素」は実在する。
10. `overrides[].rule` は共通仕様の `rules[].id` に実在する（重複宣言は不可）。
11. 実装語（フレームワーク名・関数名・HTTPステータス番号）が文字列値に混入していない。

第二層の検査項目（`lint_screens.py` = 全ファイル横断）:

1. 画面IDが全ファイルで一意。
2. navigation の from / to が実在する画面仕様書を指す（存在しない画面への遷移の検出）。
3. 到達可能性: どこからも遷移されない孤立画面の検出（入口画面は `--roots` で宣言する）。

## 生成物（手書きしないもの）

`generate.py` が画面仕様書から次を生成する。個別仕様との二重管理・乖離が構造的に起きない。

- 画面一覧: 各仕様書の id / title / status から生成。
- 画面遷移図: navigation の参照から Mermaid で生成。
- 入出力一覧: 要素の dataRef（テーブル・カラム）の集計から生成。
- Excel 出力: 納品形式として Excel が要求される場合のみ、変換スクリプトで出力する。
  Excel は編集するソースではなく出力フォーマットの一つとする。

## バージョンと拡張

`schemaVersion` は現在 "2.0"。スキーマを非互換に変更する場合に上げる。v1.x からの主な非互換は、
kind の enum 化、種別ごとの記述義務、振る舞い4値の排他と全域性、navigation の画面ID限定である。
`type` は現在 "screen" のみ。将来、画面以外の仕様（バッチ処理など）に広げる余地として持つ。

## 各スキルが上乗せするルール（スキーマには書かない）

スキーマは「あり得る形」を定義する。各スキルは、そのうちどう使うかを自身のルールで定める。

- `spec-from-code`: 生成直後は必ず `status: "draft"` を付ける。判断できなかった箇所には
  `undefined: true` を付け、生成時に人間へ報告する。意図メモ・仕様書とコードの食い違いは
  実装乖離レポートに記録する。
- `spec-to-test`: `undefined: true` の箇所は openIssues に隔離する。`notApplicable` のセルは
  テストを導出しない（発生し得ないことのレビューは仕様段階で済んでいる）。状態×イベントの
  全分岐から、テストケースを導出する。
