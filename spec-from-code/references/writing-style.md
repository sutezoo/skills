# 文章規約: 画面仕様書の生成

生成する画面仕様書（JSONの各文字列値、およびViewerで読まれる文面）の文章品質を揃える規約。

土台として、日本語の表記ルールはJTF日本語標準スタイルガイド（CC BY 4.0、一般社団法人 日本翻訳連盟）に
従う。敬体/常体の統一、句読点、漢字とかなの使い分け、全角半角、長音などは土台に委ね、
本ファイルではこの仕様書に固有の事項だけを定める。

## 1. 最重要原則: 実装の写しではなく、画面の振る舞いへ翻訳する

入力はコードだが、出力は「コードを知らない人が読んで完結する画面仕様書」である。
コードの語彙を仕様書に持ち込んではならない。コードから読み取った事実を、画面の振る舞いの言葉に
翻訳する。

| コードの語彙（NG） | 仕様の言葉（OK） |
| --- | --- |
| `max_length=50` / `maxLength={50}` | 50文字以内 |
| HTTPステータス409 | 他の利用者が先に更新していた場合 |
| HTTPステータス400 | 入力内容に誤りがあった場合 |
| `useState` / `setState` | （状態として記述。実装語は出さない） |
| serializer / view / ハンドラ | （登場させない。画面の挙動として書く） |
| `window.location.reload()` | 画面を再読み込みする |
| 非同期ジョブ / Celery / ポーリング | 処理の完了を待つ（待ち状態として記述） |

判断の指針: その語を、コードを見たことのない人が理解できるか。できないなら翻訳が足りない。
フレームワーク名・関数名・変数名・HTTPステータス番号・内部実装の手段は、仕様書に現れてはならない。

## 2. サーバ・クライアントを区別しない

これは画面の振る舞い仕様である。入力検証が画面側で行われるか通信先で行われるかは、
利用者から見れば関係ない。メールアドレスの重複のような通信先でしか判定できない検証も、
画面に現れるエラーの一つとして、他の検証と区別せず並べる。

## 3. 確度を示すタグは付けない

各記述に「事実」「推定」のようなタグを付けない。生成した仕様書は全体が実装からの読み取りであり、
人間が全体をレビューして確定させる前提である。タグはレビュー時に削除の手間を生み、
「事実」タグはかえって誤った安心感を与える。

コードから判断できなかった事項だけは、別の扱いをする（§4）。

## 4. 判断できないことは undefined で示し、断定で書かない

コードから読み取れることは断定で書く。「〜と思われる」「〜だろう」などの推測の語尾は使わない。
コードから判断できないこと（画面の利用目的、未実装の挙動、特定できない遷移先など）は、本文に
推測で埋めず、該当する振る舞いに `undefined: true` を付ける（スキーマ参照）。空にできる項目は空にする。
これらは生成時に人間へ報告する。

## 4.5. 「該当なし」の理由は根拠を書く

`notApplicable` の reason には、そのイベントが発生し得ない根拠を書く（例: この状態では保存ボタンが
非表示のため）。「特になし」「対象外」のような根拠の無い理由を書かない。理由はレビューで
「本当に発生し得ないか」を判定する材料になる。

## 5. 避ける表現

- 絵文字を使わない。
- 文中の語を目立たせる目的の強調（太字など）を使わない。
- 大仰な比喩・口語を使わない（「写し」「炙り出す」「黙って再試行」など）。
- 評価・印象の語を使わない（「強力な」「画期的な」など）。観測できる事実だけを書く。
- 英語直訳を避ける（「〜の源 / source of」「サポートする / support」など）。日本語の技術文書で
  定着した語を使う。

## 6. 振る舞いの記述（process フィールド）

- 動作として「〜する」で終える。「取得した値を各入力欄に表示する」のように、外部から観測できる
  画面の動きを書く。内部でどう実現するかは書かない。
- 一つの process には一つの動作だけを書く。複数の結果に枝分かれするなら branches で分ける。

## 7. メッセージ（message・validation の message）

- コードに文字列リテラルとして存在するメッセージは、一字一句そのまま転記する。
  これはテスト時の期待値になるため、言い換えてはならない。
- コードに存在しないメッセージを創作しない。表示があるはずだが文言が特定できない場合は、
  その旨を undefined 扱いとし、創作で埋めない。

## 8. 用語の統一

後段のテスト仕様書生成（spec-to-test）と用語を揃える。下流の文書が上流から作られる関係は
「導出」で統一する。「源」「ソース」「もとネタ」は使わない。

- 導出元: ある文書を作る基になった上流の文書（例: この画面仕様書はテスト仕様書の導出元である）。
- 導出する / 基にする: 上流から下流を作る（例: 画面仕様書を基にテスト仕様書を導出する）。

ドメイン用語（画面名・状態名・要素名など）は画面上の呼称を使い、実装の変数名をそのまま使わない。
