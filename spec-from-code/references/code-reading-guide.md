# コードの読み方ガイド: React + Django

画面の振る舞いは、フロントエンド単体では復元できない。フロントのイベントが通信先で
同期的に処理されるか、待ちを伴う処理になるかで、画面が取りうる状態が変わるためである。
フロントとバックを縦断して読み、一つの画面の振る舞いを組み立てる。

## 読む順序

1. 対象画面のフロントエンド・コンポーネントを起点にする。
2. そこから呼ばれる通信（API呼び出し）を特定する。
3. 通信先のバックエンド（ルーティング→ビュー→シリアライザ→必要なら非同期タスク）を追う。
4. 通信の結果がフロントの状態をどう変えるかを突き合わせる。

## フロントエンド（React）から抽出するもの

| 抽出対象 | 読む場所 | スキーマの対応 |
| --- | --- | --- |
| コンテナ | 複数要素をまとめる単位（ダイアログ、モーダル、テーブルなど） | children を持つトップレベル要素 |
| 単独要素 | ページに直接置かれたボタン・入力欄や、グローバルなトースト | children を持たないトップレベル要素 |
| 個別要素 | コンテナ内・トップレベルを問わず、すべての要素を漏れなく拾う | element |
| 状態 | useState の状態定数、状態を表す変数 | states |
| 状態ごとの見え方 | 条件レンダリング（`state === X && ...`）、disabled 属性 | displayByState の visibility |
| イベント | onClick, onChange, onSubmit などのハンドラ | events、behaviorMatrix |
| 要素起点のイベント | どの要素のハンドラで起きるか | behaviorMatrix の source（コンテナ/要素） |
| 処理と遷移 | ハンドラ内の setState と副作用 | behaviorMatrix |
| 入力制約 | maxLength, required, 正規表現、長さ比較 | children[].constraints |
| エラーメッセージ | エラー表示に渡される文字列リテラル | children[].validations[].message |
| 通信 | fetch / axios などの呼び出しと、レスポンスの分岐 | behaviorMatrix（通信結果の branches） |
| 画面遷移 | ルーティング操作（navigate など） | navigation（from/to は画面ID） |
| 一覧の0件時挙動 | 空配列時の条件レンダリング（`items.length === 0 && ...`）、空状態コンポーネント | elements[].emptyBehavior |

要素は漏れなく拾う。ページに直接置かれたボタン・入力欄や、グローバルなトーストはトップレベルの
単独要素として置く。複数要素のまとまり（ダイアログ・バナーなど）だけをコンテナにし、その中の
ボタン・メッセージ・入力欄を個別要素として挙げる。すべての要素を入れる包括的な「本体」のような
器は作らない。コンテナをひとことで潰さない。子が1つしかないバナーやトーストは単独要素にする。
状態ごとの見え方は、表示の有無と操作可否を分けず visibility の1値で表す
（hidden / visible / operable / conditional）。

注意: useState の状態定数は実装語なので、状態名は画面の意味を表す日本語に翻訳する
（例: `S.UPLOADING` → 「アップロード中」）。コンテナ・要素名も実装語でなく画面上の呼称にする。

## バックエンド（Django / DRF）から抽出するもの

| 抽出対象 | 読む場所 | スキーマの対応 |
| --- | --- | --- |
| 同期か非同期か | ビューが結果を返すか、タスクを起動して受付応答を返すか | states（待ち状態の有無を左右する） |
| 入力検証 | シリアライザのフィールド定義・validateメソッド | elements[].constraints, validations |
| エラー条件と応答 | ビューの分岐、例外、バリデーションエラー | behaviorMatrix の branches |
| 検証メッセージ | バリデーションエラーで返す文字列 | validations[].message |
| 競合・整合の検出 | バージョン照合、楽観ロック、重複チェック | validations または branches |
| データの参照先 | シリアライザのフィールド → モデルのフィールド（テーブル・カラム） | elements[].dataRef |

### 同期/非同期の見分けが状態を決める

ビューが処理を実行して結果を返すなら、フロントは「通信中 → 完了/エラー」の単純な状態で足りる。
ビューが処理を別の仕組みに渡して受付応答だけ返すなら、フロントは結果を後から取りに行く。
この場合「処理待ち」のような持続状態が生まれる。バックを読まないとこの状態の存在に気づけない。

## 縦断して初めて分かること（フロント単体では書けない）

- 待ち状態の有無（バックが同期か非同期か）。
- 通信結果の分岐の全体像（フロントが拾うステータスと、バックが返しうるステータスの突き合わせ）。
- 検証の二重性（フロントとバックの両方で検証している項目、どちらか一方だけの項目）。
- 検証メッセージの正確な文言（フロントが固定文言を持つか、バックの文言を表示するか）。

## 「発生し得ない」の判断（notApplicable の根拠）

behaviorMatrix は全状態×全イベントのセルを埋める（全域性）ため、コードから「この状態ではこの
イベントは発生し得ない」と判断できるセルは `notApplicable` に理由を書く。根拠はコードから取る。

- その状態で発生源の要素が非表示・操作不可（displayByState が hidden / visible）。
- その状態に至る経路上でイベントの前提となる処理が開始されていない（例: 保存処理が走っていないので
  「保存結果の受信」は起きない）。
- イベントが画面表示時にのみ発生する（例: 初期値の取得）。

根拠が displayByState の値と矛盾する notApplicable（要素は operable なのに「発生し得ない」）は
書かない。発生するが何も起きないなら process「何もしない」、判断がつかないなら undefined にする。

## 判断できないものの扱い

コードを縦断しても決まらないものは、推測で埋めない。`undefined: true` を付けるか空にして、
生成時に人間へ報告する。典型例:

- 画面の利用目的・利用者（コードには現れない）。
- この画面への入口、保存後の遷移先（呼び出し側のルーティング次第で、対象画面のコードにない）。
  navigation は画面ID（SCR-NNN）でしか書けないため、遷移先画面のIDが特定できないときも空にする。
- 異常系の未実装挙動（取得失敗時に何も定義されていない、など。これは「定義されていない」という
  事実として undefined にする）。
- 表示はあるが文言が動的で特定できないメッセージ。
