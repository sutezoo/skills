# 意図メモ ガイド

意図メモは、画面ごとに、コードから独立した意図を数行から十数行で書いた短文の集合である。
フル仕様ではなく、コードを裁く基準（オラクル）であり、spec-from-code の to-be 入力になる。

## なぜ要るか（オラクルの独立性）

コードだけから仕様を起こし、その仕様からテストを導出すると、テストは「コードがやっていることを、
コードがやっているか」の確認になる。実装と同じ情報源から生成されたテストは実装と盲点を共有するため、
いま存在するバグを検出できない。判定の基準が実装から独立していないためである。

意図メモは、実装に着手する前（または実装と独立に）書かれた意図の記録として、この独立性を確保する。
spec-from-code は意図メモを to-be、コードを as-is として突き合わせ、食い違いを実装乖離レポートに
記録する。乖離は spec-to-test で to-be を期待値とするテストになり、未修正のコードでは fail する。
この仕組み全体が、意図メモの存在を前提にしている。

## 書式: EARS の日本語テンプレート

書式は EARS（Easy Approach to Requirements Syntax）の5パターンを日本語テンプレート化して固定する。
テンプレートを固定しているため、人間が書いてもエージェントに書かせても言い回しが揺れない。

| パターン | テンプレート | 例 |
| --- | --- | --- |
| 常時 | システムは常に〜すること | システムは常に検索条件に合致する全件数を表示すること |
| イベント駆動 | 〜したとき、システムは〜すること | 検索したとき、結果を一覧に表示すること |
| 状態駆動 | 〜の間、システムは〜すること | 検索処理の間、検索ボタンは押せないこと |
| 望ましくない挙動 | もし〜の場合、システムは〜すること | 結果が0件の場合、「該当する灯台がありません」と表示すること |
| オプション | 〜を備える場合、システムは〜すること | 管理者権限を備える場合、削除ボタンを表示すること |

## 書き方のルール

- 1画面1ファイル。ファイル名は `<画面ID>.intent.md`（例: `SCR-030.intent.md`）とする。
- 1行1文。各行が上の5パターンのいずれかに当てはまること。当てはまらない文は分解するか書き直す。
- 数行から十数行に収める。フル仕様を書かない。網羅は画面仕様書（screen-spec）の仕事であり、
  意図メモは「これだけは外せない」意図の記録に徹する。
- 画面に出る文言（エラーメッセージなど）を意図として持つ場合は、鉤括弧で文言そのものを書く。
  これがテストの期待値になる。
- 実装語（フレームワーク名・関数名・HTTPステータス番号）を書かない。
- 書く時期は要件確定の時点が理想。実装後に書く場合も、コードを見ずに、要件と記憶から書く
  （コードを見て書くと独立性が失われ、乖離検出が空振りする）。

## 記述例

```markdown
# SCR-030 灯台検索画面 意図メモ

- 画面を開いたとき、すべての灯台を検索結果として表示すること
- 検索したとき、適用中のフィルタをチップで表示すること
- 検索結果が0件の場合、「該当する灯台がありません」と表示すること
- 検索処理の間、検索ボタンは押せないこと
- もし竣工日に存在しない日付が入力された場合、「竣工日は正しい日付で入力してください」と表示すること
```

## spec-from-code での使われ方

- 意図メモは正準ソースの最上位（意図メモ ＞ 要件定義書 ＞ 手書き仕様書 ＞ コード）。
  詳細レベルの意図はここにしか存在しないことが多い。
- メモの各行はコードと突き合わせ、一致すれば spec に反映、食い違えば to-be を spec に反映して
  実装乖離レポートに1件記録する。
- メモに無い詳細（メモは網羅しない）はコードから補う。これは正常であり、乖離ではない。
- 意図メモが無い場合、to-be の情報源が実質空になり、生成される仕様書はコードの鏡写しになる。
  spec-from-code はその旨を明示的に警告する（黙って進めない）。
