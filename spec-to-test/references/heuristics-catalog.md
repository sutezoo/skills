# 横断観点カタログ（Cross-cutting Test Heuristics）

ブラウザで動くWebアプリで、**機能仕様書(spec)に書かれていなくても確認すべき汎用観点**を網羅的にカタログ化したもの。
spec 起点（演繹）では出てこない「知識依存の観点」（絵文字入力、長文字列のレイアウト崩れ、二重送信、ゼロ件表示…）を、ここから機械的に注入する。

## このカタログの使い方（重要）

設計思想は **「広く持って、ルールで引き算する」**。発想に頼らず、漏れを構造的に防ぐ。

1. **網羅優先で持つ**: このカタログは「全部入り」。プロジェクトで使わない観点も削らず残す。
2. **プロジェクト単位で除外する**: 使わない大分類/観点は `project-profile.json` で**理由付きで**除外宣言する（例: 多言語非対応 → I18N 除外）。裁量でその場で省かない。
3. **要素の kind で自動適用する**: 残った観点は §16「kind → 観点マッピング」に従い、画面の項目・要素の型から機械的に当てる。誰がやっても同じ観点が当たる。
4. **黙って落とさない**: 適用も除外も非該当も、test-spec の「横断観点カバレッジ表」に記録する。消すのではなく「除外（理由）」として残し、レビュー対象にする。

> 出典の考え方: Elisabeth Hendrickson らの Test Heuristics（データ型攻撃・Webテスト・ヒューリスティクス）を骨格に、ISO/IEC 25010 の品質特性と、日本語Webアプリ特有の文字種を加えて再構築している。各観点は「なぜ要るか」を説明できる状態に保つこと。

## 観点の持ち方（3点セット）

各観点は名前だけだと適用がブレる。必ず次の3点を持たせる:

- **適用トリガー**: どんな項目・画面要素なら当てるか（型マッピングの条件）
- **確認内容**: 何が起きていれば合格か（test-spec の期待結果の素になる）
- **データ例**: 実際に流す具体値（絵文字、長文字列など。コピペで使える粒度）

## STR — 文字列・文字種

適用トリガー: テキスト入力（単一行・複数行）、検索ボックス、名前/件名などの自由入力。

| ID | 観点 | 確認内容 | データ例 |
| --- | --- | --- | --- |
| H-STR-01 | 空・空白のみ | 必須なら適切なエラー、任意なら正しく空として扱う | ``（空）, 半角スペースのみ, 全角スペースのみ |
| H-STR-02 | 前後の空白 | トリムされるか／そのまま保存か仕様どおりか | `  値  `, 末尾改行 |
| H-STR-03 | 最大長ちょうど・超過 | 上限で受理、超過で適切に拒否（境界値と連動） | maxちょうど, max+1, 極端な長文 |
| H-STR-04 | 極端な長文字列 | 保存・表示・通信が壊れない（DISP-03と連動） | 5,000字, 100,000字 |
| H-STR-05 | 改行・タブ・制御文字 | 改行コード混在・タブ・制御文字で崩れない | `行1\r\n行2`, `a\tb`, `\0`, ベル文字 |
| H-STR-06 | 特殊記号 | 記号類を含んでも保存・表示・検索が壊れない | `< > & " ' / \ \| % # ? * ; :` |
| H-STR-07 | 空白の連続・種類 | 連続空白の畳み込み有無、タブ/全角/NBSPの扱い | `a   b`, NBSP(`\u00A0`), 全角空白 |
| H-STR-08 | 大文字小文字 | 比較・検索・一意制約での大小区別が仕様どおり | `ABC` vs `abc`（重複判定・検索ヒット） |
| H-STR-09 | 先頭・末尾の特殊文字 | 先頭がハイフン/記号/数字でも壊れない | `-開始`, `=式`, `@先頭` |

<a id="i18n"></a>
## I18N — 国際化・文字コード（日本語Webアプリで特に効く）

適用トリガー: テキスト入力／表示。**多言語対応しないプロジェクトでも、日本語のサロゲートペア・正規化・全角半角は除外しないこと**（日本語環境で普通に発生するため）。RTL・他言語は多言語対応時のみ。

| ID | 観点 | 確認内容 | データ例 |
| --- | --- | --- | --- |
| H-I18N-01 | 絵文字・サロゲートペア | 4バイト文字が保存・表示・文字数カウントで壊れない（DBが`utf8`でなく`utf8mb4`か等） | 😀, 𠮷(つちよし), 𩸽(ほっけ), 🇯🇵 |
| H-I18N-02 | Unicode正規化（NFC/NFD） | 濁点分離・結合文字で検索ヒット/重複判定がずれない | `が`(NFC) vs `か+゛`(NFD), `ペ` 分解形 |
| H-I18N-03 | 全角・半角 | 全角英数/半角カナの入力・検索・重複判定が仕様どおり | `ＡＢＣ123`, `ﾊﾝｶｸ`, `１２３` |
| H-I18N-04 | 異体字・機種依存文字 | 異体字セレクタ・丸数字・ローマ数字で壊れない | `葛`+異体字セレクタ, `①`, `Ⅳ`, `㍻` |
| H-I18N-05 | ゼロ幅・不可視文字 | ゼロ幅スペース等が混入しても検知/除去されるか | `\u200B`(ZWSP), `\uFEFF`(BOM) |
| H-I18N-06 | 双方向テキスト(RTL) | アラビア語/ヘブライ語混在で表示が破綻しない（多言語対応時） | `العربية`, `שלום` + 日本語混在 |
| H-I18N-07 | 文字数カウント基準 | サロゲート/結合文字を1文字と数えるか、上限判定と一致するか | 絵文字を上限ちょうど含む文字列 |

## 16. kind → 観点マッピング（運用の起点）

spec JSON の各 `elements[].kind` を下表に当てはめ、対応する観点群を自動適用する。
`kind` は画面により語彙が増えるので、表に無いものは**意味カテゴリ**で判定する（例: 「日付ピッカー」→ 日付・時刻入力）。
「画面共通」はその画面に一度ずつ当てる。project-profile で除外された大分類は飛ばす。

| elements[].kind（例） | 意味カテゴリ | 自動適用する観点 |
| --- | --- | --- |
| テキスト入力 | 文字列入力（単一行） | H-STR-01〜09, H-I18N-01〜05/07, H-SEC-01/02/05 |
| テキストエリア | 複数行テキスト | H-STR-01〜09, H-I18N-01〜05/07, H-DISP-03, H-SEC-01/02 |
| 数値入力 | 数値入力 | H-NUM-01〜06, H-STR-01（空）, H-SEC-05 |
| 日付入力 / 日付ピッカー | 日付・時刻入力 | H-DATE-01〜07, H-STR-01（空） |
| セレクト / ラジオ / チェックボックス | 選択・候補 | H-SEL-01〜06 |
| ファイル入力 | ファイル | H-FILE-01〜05 |
| 一覧 / テーブル / リスト | 一覧表示 | H-DISP-01〜08, H-NAV-02/03 |
| ボタン（送信・確定系） | 送信ボタン | H-NAV-01/08, H-CONC-04/05, H-NET-01〜06 |
| 表示テキスト / カウンタ / ラベル | 表示 | H-DISP-03/04/08 |
| バナー / 通知トースト | 通知表示 | H-DISP-04, H-NET-01（エラー通知の整合） |
| （behaviorMatrix で状態×イベントを持つ要素/画面） | 並行・状態 | H-CONC-01〜05 |
| （認証・権限が絡む画面） | 権限 | H-NFR-03, H-CONC-03, H-NAV-04, H-SEC-03/04 |
| （画面共通: 全画面に一度） | 画面全体 | H-NAV-02〜07, H-NET-01/02/06, H-ENV-01〜06, H-A11Y-01〜05, H-NFR-01 |

### 適用の手順（再現性のため固定）

1. spec JSON の `elements[]`（`kind`・`constraints`・`validations`）と `behaviorMatrix` を見て、各要素を上表の kind / 意味カテゴリに分類する。
2. kind ごとに対応観点を引く。**画面共通**を画面に一度当てる。状態（`states`/`behaviorMatrix`）を持つなら H-CONC を当てる。
3. `project-profile.json` の `exclusions[]` に該当する観点を外す（記録は残す）。
4. 残った観点をテスト仕様書(JSON)の `viewpoints[]` に起こす。`category: "横断観点"`、`catalogIds: [...]` に由来を記す。
5. 適用・除外・非該当を `crossCuttingCoverage[]` に記録する。**黙って落とした観点が無い**状態にする。

### テスト仕様書(JSON)への落とし込み方

横断観点は独自ID体系を作らず、**既存の `viewpoints[]` に統合**する。区別は `category` と `catalogIds` で行う:

- `viewpoints[].category` に **`"横断観点"`** を使い、`catalogIds` に由来（`["H-I18N-01", ...]`）を記す。
- **入力値系**の横断観点（文字種・絵文字・長さ等）は、その要素の `equivalenceClasses` の**無効クラスに吸収**してよい（例: H-I18N-01 → `{ "kind": "invalid", "condition": "絵文字を含む" }`）。`crossCuttingCoverage[]` に「H-I18N-01 → EC-Ixx で被覆」と記録する。
- **画面挙動系**（戻る/リロード/二重送信/同時編集/ゼロ件表示等）は、独立した `viewpoints[]` として起こす（`technique: "単独確認"`、または `decisionTables`/`stateTransitions`）。

> 要するに「入力値の異常系は equivalenceClasses に溶かす／画面挙動系は独立 viewpoint にする」。どちらでも `crossCuttingCoverage` で catalogId が追跡できれば再現性は保てる。
