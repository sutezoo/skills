# wording-rules — 期待値・前提条件を「テスターに伝わる文」にする

test-items の `expected`（期待値）・`precondition`（前提条件）・`operation`（操作）が、
「期待値：操作できること」のように**痩せすぎてテスターに伝わらない**のを防ぐ記述規則。

## スコープ

- これは**文章表現の規則**。項目（欄）は増やさない。`expected`/`precondition` は自由文字列のままで、**schema は変更しない**。
- 対象は「**spec に情報は在るのに、表現だけが痩せている**」ケース。在る情報（要素名・状態名・メッセージ文言）を観測可能な文に整えるだけ＝*捏造ではない*。
- 「観測できる期待値そのものが spec に無い」場合は、ここで埋めない。**openIssues に隔離 → spec-from-code に戻す**（§5）。これがアンチパターン「spec を書き直す／推測で埋める」を守る境界線。

---

## 1. 中核原則 — 観測可能 × 自己完結

テストケースの読み手は複数いる（実行者・レビュアー・開発者）。全員に伝わらなければ意味がない。期待値が曖昧だと合否が主観に流れる。だから 1 文ごとに次を満たす。

- **観測可能（observable）**: 画面の*何を見れば*合否が決まるかが書いてある。内部の能力（「〜できる」）で止めない。
- **自己完結（self-contained）**: その文だけで判定できる。テスターが screen-spec を読み返さなくてよい。

「操作できること」はこの両方を外している（何が・どう変われば「できた」のかが無い）。

---

## 2. 期待値（expected）の記述規則

1. **主語は画面上の要素**にする（「保存ボタンが」「エラー表示が」）。「システムが」「正常に」で始めない。
2. **観測できる結果**を書く。状態変化・表示の出現/消滅・遷移先・値の変化など、画面で確認できる事実に落とす。
3. **メッセージが出るケースは文言をそのまま載せる**。「エラーになる」ではなく「『表示名を入力してください』が表示される」。
4. **1 期待値＝1 検証事実**。「保存され、かつ一覧に戻る」のような複合は分割（合否が「一部OK」に化けるのを防ぐ）。
5. **遷移後の状態を明記**する（状態を持つ画面）。「保存中状態になり、保存ボタンが非活性になる」のように落ち先まで書く。

### 悪い例 → 良い例

| 悪い（痩せている） | なぜダメか | 良い（観測可能・自己完結） |
| --- | --- | --- |
| 操作できること | 何が変われば合格か不明 | 保存ボタンが活性になり、押下できる |
| 正常に保存される | 「正常」が観測不能 | 保存後に「保存しました」が表示され、表示状態に戻る |
| エラーになる | どこに何が出るか不明 | 「表示名を入力してください」が表示され、状態は編集可能のまま変わらない |
| 値が反映される | 反映先・確認箇所が無い | 一覧の表示名欄が、入力した「山田太郎」に更新される |
| 画面が変わる | 遷移先が無い | 確認画面（SCR-031）に遷移する |
| ボタンが押せなくなる | 状態名・対象が曖昧 | 保存中状態になり、保存ボタンが非活性（グレーアウト）になる |
| 保存され、一覧に戻る | 複合期待値 | （2ケースに分割）①保存後に「保存しました」が表示される ②表示が一覧画面に戻る |

---

## 3. 前提条件（precondition）の記述規則

1. **状態ラベルだけで終わらせない**。「編集可能状態」で止めず、テスターがその状態に**どう到達できるか／何が成立していればよいか**まで書く。
2. **操作（operation）と混ぜない**。前提を手順に紛れ込ませると、テスターは実行の途中で条件不足に気づく事故になる。役割を分けて書く。
3. **判定に効く前提だけ**を、過不足なく。無関係な前提を並べてノイズにしない。

### 悪い例 → 良い例

| 悪い（痩せている） | なぜダメか | 良い（到達手順 or 成立条件が分かる） |
| --- | --- | --- |
| 編集可能状態 | どう作る状態か不明 | プロフィール編集画面を開き、表示名が編集可能（未保存）な状態 |
| ログイン済み | 誰として、どの権限か | 一般ユーザー「testuser」でログイン済み |
| データがある状態 | 何のデータが何件か | 一覧に既存の表示名レコードが1件以上ある状態 |
| 保存中 | 受動的すぎて再現不能 | 保存を実行し、応答待ち（保存中状態）になっている |

---

## 4. 操作（operation）・入力（input）の補助規則

期待値・前提を直しても、操作と入力が曖昧だと再現できない。最低限そろえる。

- **operation**: テスターの行動を一意に。「保存する」→「保存ボタンを押下する」。前提（§3-2）を混ぜない。手順は*必要な粒度*に留め、過剰に細かくしない（手順消化が目的化して観点を見失う）。
- **input**: 値は具体に。境界値は実値で（例: 0文字／1文字／50文字／51文字）。「長い文字列」ではなく「51文字の表示名」。

---

## 5. 「整形してよい」か「上流に戻す」かの判定（捏造防止の核）

```
expected/precondition が痩せている
        │
        ├─ spec に要素名・状態名・メッセージ文言が「在る」
        │        → 在る情報を観測可能な文に整形する（§2–§4）。転記の精緻化であり捏造ではない。
        │
        └─ 観測できる期待値そのものが spec に「無い」
                 （出るべきメッセージ文言が未定義 / 遷移先が未定義 / 合格状態が未定義）
                 → 整形で埋めない。openIssues に隔離し、spec-from-code に差し戻す。
                   推測で書くと根拠のない期待値になる（アンチパターン）。
```

判定の問い: **「この文を観測可能にするのに必要な事実は、screen-spec の中に在るか？」**
在るなら整形、無いなら差し戻し。

---

## 6. チェックリスト（生成時・レビュー時）

```
[期待値 expected]
- [ ] 主語が画面上の要素になっている（「〜が」）
- [ ] 観測できる結果になっている（「〜できる」で止まっていない）
- [ ] メッセージ系は文言をそのまま載せている
- [ ] 1ケース1検証事実（複合期待値になっていない）
- [ ] 状態遷移系は遷移後の状態まで書いてある
- [ ] この文だけで合否判定でき、specを読み返さなくてよい

[前提条件 precondition]
- [ ] 状態ラベルだけで終わっていない（到達手順 or 成立条件がある）
- [ ] 操作(operation)が紛れ込んでいない
- [ ] 判定に効く前提だけが、過不足なく書かれている

[操作・入力]
- [ ] operation でテスターの行動が一意に特定できる
- [ ] input が具体値（境界値は実値）

[出どころの正当性]
- [ ] 整形に使った事実は screen-spec に実在する（捏造していない）
- [ ] specに無い期待値は埋めず、openIssues に隔離している
```
